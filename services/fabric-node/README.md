# bloodchain-fabric-node

Hyperledger Fabric gateway service for **Bloodchain** — the national blood-supply
management platform of the Republic of Botswana (Ministry of Health).

This service anchors verified blood donation events on an immutable distributed
ledger. It sits alongside the Bloodchain `api-server`, which calls it whenever a
Rubric operator verifies a donation.

## Project Overview

- **Name**: bloodchain-fabric-node
- **Role**: Blockchain immutability layer on top of the primary Postgres database
- **Stack**: Node.js 20 · TypeScript 5 · Express 5 · `@hyperledger/fabric-gateway` · Go 1.21 chaincode
- **Port**: 3001

### Why blockchain?

Postgres remains the primary database. Fabric is an **independent immutability
layer**: once a donation is anchored, no operator — including Bloodchain
employees — can retroactively change it. The public ledger endpoint requires no
authentication, so investors, regulators, and partner hospitals can
independently verify platform activity.

## API

| Method | Path | Auth | Description |
|---|---|---|---|
| `POST` | `/fabric/donations` | Bearer | Anchor a verified donation on the ledger (201 / 409 duplicate / 400 / 503) |
| `GET` | `/fabric/donations/:txId` | Bearer | Fetch a single donation record (200 / 404) |
| `GET` | `/public/ledger?limit=20&bookmark=` | none | Paginated public feed, newest first. `Cache-Control: public, max-age=15` |
| `GET` | `/public/stats` | none | `{ totalDonations, uniqueDonors, uniqueCentres }`. `Cache-Control: public, max-age=30` |
| `GET` | `/healthz` | none | Health check — reports `ledgerMode: "mock" \| "fabric"` |

### POST /fabric/donations — request body

```json
{
  "txId": "uuid generated by the api-server",
  "donorHash": "64-char SHA-256 hex of clerk_user_id",
  "centreId": "CTR-GAB-001",
  "centreName": "Princess Marina Hospital",
  "district": "Gaborone",
  "bloodType": "O+",
  "donatedAt": "2026-08-29T10:00:00.000Z",
  "operatorHash": "64-char SHA-256 hex of operator clerk_user_id"
}
```

Valid blood types: `O+ O- A+ A- B+ B- AB+ AB-`. Success response (201):
`{ "success": true, "blockHeight": "12345", "ledgerTimestamp": "..." }`

## 1. Running in mock mode (Replit / Render / local)

```bash
cp .env.example .env          # set FABRIC_GATEWAY_SECRET (openssl rand -hex 32)
npm install
npm run dev                   # tsx watch (development)
# — or —
npm run build && npm start    # compiled production run
```

With `FABRIC_MOCK_MODE=true` (default) all chaincode calls are simulated by an
in-memory ledger seeded with 6 realistic Botswana donation records — the public
ledger is never empty on first boot. No Fabric network is required. The real
Fabric connection code still exists and is exercised the moment mock mode is
turned off.

> ⚠️ The mock ledger is in-memory: it resets on every restart. It exists for
> demos and integration testing only.

## 2. Connecting to a real Fabric test-network

1. Bring up the [fabric-samples test-network](https://github.com/hyperledger/fabric-samples):
   ```bash
   ./network.sh up createChannel -c mychannel -ca
   ```
2. Deploy the chaincode in `chaincode/bloodchain/`:
   ```bash
   ./network.sh deployCC -ccn bloodchain -ccp /path/to/chaincode/bloodchain -ccl go
   ```
3. Base64-encode the credentials of an Org1 user and export them:
   ```bash
   export FABRIC_MOCK_MODE=false
   export FABRIC_PEER_ENDPOINT=localhost:7051
   export FABRIC_PEER_HOST_ALIAS=peer0.org1.example.com
   export FABRIC_MSP_ID=Org1MSP
   export FABRIC_TLS_CERT=$(base64 -w0 organizations/peerOrganizations/org1.example.com/peers/peer0.org1.example.com/tls/ca.crt)
   export FABRIC_CERT=$(base64 -w0 organizations/peerOrganizations/org1.example.com/users/User1@org1.example.com/msp/signcerts/*.pem)
   export FABRIC_KEY=$(base64 -w0 organizations/peerOrganizations/org1.example.com/users/User1@org1.example.com/msp/keystore/*)
   ```
4. Start the service. It probes the peer at startup (`GetLedgerStats`); if the
   peer is unreachable it logs a clear error and **falls back to mock mode**
   rather than crashing. Runtime peer failures on individual transactions
   return **503 Service Unavailable** — never a silent `success: true`.

## 3. How the api-server calls this service

After marking a donation verified in Postgres (`donor_donations.verified=true`):

```ts
const txId = crypto.randomUUID();
const res = await fetch('https://fabric-node.bloodchain.app/fabric/donations', {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${process.env.FABRIC_GATEWAY_SECRET}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({
    txId,
    donorHash: sha256(clerkUserId),        // hash BEFORE sending — never send raw IDs
    centreId, centreName, district, bloodType,
    donatedAt: donation.verifiedAt.toISOString(),
    operatorHash: sha256(operatorClerkUserId),
  }),
});

if (res.status === 201) {
  const { blockHeight } = await res.json();
  // write txId + blockHeight back into the donor_donations row
} else if (res.status === 409) {
  // already anchored (retry-safe) — treat as success, re-read the record if needed
} else if (res.status === 503) {
  // ledger write did NOT happen — flag donation as "pending ledger confirmation" and retry
}
```

**Idempotency**: retries with the same `txId` return `409 Conflict` and never
create duplicate ledger entries.

## 4. FABRIC_GATEWAY_SECRET — usage and rotation

- A random 64-char hex string shared between the api-server and this service.
- Sent as `Authorization: Bearer <secret>` on all `/fabric/*` routes.
- Compared with `crypto.timingSafeEqual` (hashed to equal length first) to
  prevent timing attacks.

**Generate**: `openssl rand -hex 32`

**Rotate** (brief write-window interruption, public reads unaffected):
1. Generate a new secret.
2. Update `FABRIC_GATEWAY_SECRET` on this service (Render → Environment) and redeploy.
3. Update the same variable on the api-server and redeploy.
4. Failed writes during the window surface as 401 to the api-server, which
   should queue-and-retry (see 503 handling above — same retry path).

## Data Architecture

- **Ledger data model** (`DonationRecord`, stored as `DONATION_<txId>`):
  `txId, donorHash, centreId, centreName, district, bloodType, donatedAt, operatorHash, blockchainVerified, ledgerTimestamp`
- **Secondary index**: `DONOR_<donorHash>_<txId>` composite keys for per-donor history
- **Storage**: Hyperledger Fabric world state (channel `mychannel`, chaincode `bloodchain`); in-memory `Map` in mock mode
- **Chaincode functions**: `RecordDonation`, `GetDonation`, `GetLedgerFeed`, `GetLedgerStats`

### Design constraints (enforced)

1. **Privacy** — This service must NEVER receive or store raw Clerk user IDs.
   The api-server SHA-256-hashes them before calling. Both hashes are validated
   as 64-char hex. The public feed exposes only pseudonymous hashes — not PII.
2. **Immutability** — The chaincode has NO update/delete/overwrite functions.
   The only write is `RecordDonation`. Data entry errors are fixed by recording
   a new corrective entry, never by modifying the original.
3. **Idempotency** — Duplicate `txId` → 409, no duplicate write.
4. **Error handling** — Peer unreachable with mock mode off → 503. The ledger
   result is never misreported as success.
5. **Logging** — Structured JSON (pino). Transaction submissions log
   `txId, centreName, bloodType, blockHeight, latencyMs`; public ledger fetches
   log `ip, limit, resultCount`.

### Scalability note (not implemented — by design, for MVP)

`GetLedgerStats` performs a full ledger scan and will become slow at tens of
thousands of records. In production, replace it with either:
- a **CouchDB rich query** with indexes on `donorHash` and `centreName`, or
- a **stats state variable** incremented inside `RecordDonation`.

## Demo website widgets

Two standalone React components in `src/demo-components/` can be dropped into
the bloodchain.life React/Vite marketing site:

- **`LedgerFeed.tsx`** — live dark-themed feed of `/public/ledger` (polls every
  30 s; blood-type colour badges; relative times; truncated txIds; LIVE pulse).
- **`BlockchainStats.tsx`** — three animated stat counters from `/public/stats`
  (polls every 60 s; count-up animation; "Verified on Hyperledger Fabric" badge;
  hover tooltip).

Both accept a `baseUrl` prop, defaulting to
`import.meta.env.VITE_FABRIC_BASE_URL ?? 'https://fabric.bloodchain.app'`.
